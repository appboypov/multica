Projects organize work that takes multiple [issues](/issues) to finish — a product launch, a migration, or a feature delivered in stages.

Work that a single issue can describe does not need a project. Projects fit a group of work that shares a goal, needs its progress tracked together, or works in the same repositories.

## Parts of a project

| Part | Purpose |
|---|---|
| **Name, icon, and description** | Goal, scope, and long-lived requirements; the description enters the execution context of agents working inside the project. |
| **Organisation** | The organisation the project belongs to, or **No organisation**. |
| **Priority** | `urgent`, `high`, `medium`, `low`, or `none`. |
| **Lead** | A member or an agent — who coordinates the project. |
| **Issues and progress** | The work in the project and how much of it is finished. |
| **Repositories** | The GitHub repositories the project works in, each with its checkout and its worklanes. |

## Organisations

An organisation groups projects, for example by the company or client they serve. A project belongs to at most one organisation. **New project** asks for one, and the **Organisation** row in a project's properties changes it.

- **Projects** groups the projects by organisation, in name order, with **No organisation** last for projects without one. Click a group's row to fold it.
- **Organisations**, in the sidebar after Projects, lists every organisation with its number of projects. A row opens the organisation's page, which lists its projects; **New project** there starts the project in that organisation.
- **New organisation** asks for a name and a key. No two organisations share a name, ignoring case.
- The **key** names the organisation's folder: lowercase letters, digits and dashes, starting with a letter or digit, and unique in the workspace. Change it on the organisation's page.

Organisations can't be renamed or deleted.

## Projects and issues

A project can contain any number of issues; an issue belongs to at most one project. Create issues directly inside the project, or pick or change the project from the issue's properties.

Project progress is computed automatically from linked issues:

```text
progress = issues in done or cancelled ÷ all issues in the project
```

`cancelled` means that work has been closed out of the project's scope, so it counts toward progress.

## Project description and execution context

When an agent runs an issue inside a project, the project's name and description are added to that run's context. The description is the place for information every related issue needs: the goal, technical boundaries, delivery conventions. Requirements that apply to only one issue belong in that issue.

## Repositories

A project holds the GitHub repositories it works in. Its page shows the number of repositories in its header and one card per repository, by `owner/name`: its default branch and its worklanes, starting with `main` in the repository's checkout. Click a card's header to fold it. On **Projects** and an organisation's page, a project's row folds open to one row per repository.

- **Repository** opens **Add repository**. It lists every repository the workspace's [GitHub App](/github-integration) can see, with Private or Public and its default branch. A repository is in at most one project: one that is already in a project shows that project's name and can't be picked. **Missing one? Give Multica access on GitHub** opens the App's installation page.
- **Checkout** picks a machine and the folder of the repository's normal checkout, `~/Repos/{name}` to start with. Multica checks the folder on that machine: it must be a git checkout of the repository, on its default branch. With no folder there, **Clone it there** clones it.
- **Releases** picks where the repository's version comes from: a version file found in the checkout (`pubspec.yaml`, `Cargo.toml`, `pyproject.toml` or `package.json`), **Tags only**, or **This repository does not release**.
- **Install** picks the command that installs a new worklane's dependencies. Multica looks on the default branch for `pnpm-lock.yaml` (`pnpm install`), `package-lock.json` (`npm ci`), `yarn.lock` (`yarn install`), `pubspec.yaml` (`flutter pub get`) and `uv.lock` (`uv sync`), and offers each command it finds, the first one picked, as well as **None** and a command you type. **Edit repository** shows the saved command, and finds one when the repository has none yet.
- A card's menu has **Edit repository**, which changes the checkout and the releases but not the repository, and **Remove repository**, which removes the repository and its worklane `main` from Multica. The checkout folder stays on the machine, unchanged. A repository with worklanes besides `main` can't be removed until they are.

## Worklanes

A worklane is a lane of work in a repository, with its own git worktree on one machine. Every repository has `main`, which works in the repository's checkout.

- **Add worklane** on a repository's card, or **+ Worklane** on its row on Projects and an organisation's page, opens **New worklane · \{owner/name\}**. The **Name** is unique in the repository. **Folder** fills in from the name, in lowercase with dashes, and is unique among the repository's worklanes. **Runtime** lists the online machines that hold the repository's checkout and can make worktrees. **Worktree** shows where the worktree goes, `~/Worktrees/{organisation key}/{repository}/{folder}`, the branch it starts from and the install command.
- **Create worklane** runs each step on the machine: fetch the default branch, add the worktree, install the dependencies. A failed step keeps its error with **Try again**, and no worklane is saved until every step passes. Then the worklane's page opens.
- A worklane's page shows its repository, Busy or Free, its Timeline and its activity: who created it on which machine, each rename and the changes to its repository's releases.
- A worklane's menu has **Rename**, which keeps the folder and the worktree, and **Remove**, which deletes the worktree on its machine and removes the worklane from Multica. Remove refuses, and says why, while the machine is offline or the worktree holds uncommitted changes or commits that are not on the default branch. `main` can't be renamed or removed.
- A repository's card, its project's header and the rows on Projects and an organisation's page show how many worklanes they hold, `main` included.

## Project lead

The lead can be a member or an agent, and marks who coordinates the project. It is not a permission setting: it does not auto-assign the project's issues, and making an agent the lead does not automatically run it. Starting a run still takes an issue assignment, an @mention, or an automation trigger.

## Work in a worklane

A worklane's page shows its issues in three views. Pick one in the page's header; the page opens on **Timeline**.

- **Timeline** shows the releases of the repository's line in order, with this worklane's issues in each.
- **Board** shows the worklane's issues in a column per status, with **Cancelled** hidden. Drag a card to another column to change its status: Multica confirms with "REBL-76 moved to In Review", and puts the card back if the change fails. A column's **+** opens **New issue** with that status, the worklane and its repository's next release.
- **List** shows a section per release, in line order: its version and state, its title, **Set by hand** for a version set by hand, "1 of 3 done" over this worklane's issues in it or **No issues of this worklane**, the release menu and its description, then the issues. **No release** follows with the worklane's issues in no release, while there are any.

Click an issue in any view to open its preview beside the view. The preview starts with the type, the ID, the title, the status, the worklane, the release and the assignee, then the description. **Open issue** opens the issue's own page.

The **Type** filter in the header picks one or more of the eight types, or **No type** for issues without one. Every view then shows only the picked types, and switching views keeps them.

### Busy and Free

A worklane is **Busy** while one of its issues that is In Progress or In Review holds its worktree's branch, and **Free** otherwise. The header says what it works on:

- **now: \{ID\} \{title\}** while Busy, for the issue that holds the branch.
- **next: \{ID\} \{title\}** while Free, for the first issue that is not Done or Cancelled: the releases in line order, then No release, and within each the issue created first.
- Neither, when every issue of the worklane is Done or Cancelled.

### Agents in a worklane's worktree

An agent's task on an issue of a worklane runs in that worklane's worktree, on the issue's branch; for `main`, in the repository's checkout. A worklane runs one task at a time. A task from an agent whose runtime is on another machine than the worklane is refused, and the task says so.

When the pull request of the issue that holds the branch merges into the default branch, the worktree switches to the next issue's branch, cut from the fetched default branch, or is left detached when no issue is left. It switches only when nothing would be lost: with uncommitted changes or commits that are not pushed, it stays on its branch and the worklane's activity says why.

## Releases

A repository's releases form one line, in the order they ship. Every worklane of the repository shows the same line on its **Timeline**: the first unshipped release is **Next release** and the ones after it are **Planned**. The worklane's header says **last shipped v\{version\}**, **nothing shipped yet** or **does not release**. On Projects and on an organisation's page, each worklane row shows its repository's last and next release under **Last · Next · Planned releases**; click a release to open it on the worklane's Timeline.

- **Plan release**, at the end of the Timeline, adds a release after the last one. Pick **Patch**, **Minor** or **Major** to bump the version of the release before it, or of the last tag for the first release, or **Custom** to set the version by hand. Every version must be higher than the one before it: while it is not, the dialog says why and **Plan release** stays disabled.
- A version set by hand shows **Set by hand** and keeps its number when the line changes. A bumped version follows the release before it.
- The menu of an unshipped release offers **Edit release**, **Move earlier**, **Move later** and **Remove release**. **Edit release** changes the version, title and description. Moving or removing a release renumbers the bumped releases after it; a move that would leave a version not higher than the one before it is disabled, with the reason.
- Each change appears in the activity of every worklane of the repository, with one line for each version it changed, such as "Notifications v1.2.0 -> v1.1.0".

A release has no date and no goal before it ships.

### Repositories that do not release

Set **Releases** to **This repository does not release** in **Edit repository**, and its worklanes show "\{owner/name\} does not release, so its worklanes plan no releases." in place of Plan release. A repository can't stop releasing while its line holds unshipped releases: Edit repository names them and asks you to remove them first. Pick **Tags only** or a version file again, and Plan release starts from the last tag.

## Worklanes and Releases

**Worklanes** and **Releases** sit under Work in the sidebar, after Organisations. Both list the workspace's work by organisation, project and repository, in the order Projects shows them, and leave out anything that holds nothing to list. Every group opens unfolded; click a chevron or a group's row to fold it. An organisation's or a project's name opens its page.

- **Worklanes** lists every worklane, `main` first under each repository. Each repository shows its default branch and **+ Worklane**, which opens New worklane for it. A worklane row shows what the worklane works on and its releases: the last shipped one, the next one with "\{done\}/\{total\}" over this worklane's issues in it, and up to two planned releases after it. The row opens the worklane's Timeline.
- **Releases** lists every repository's releases that have not shipped, in line order: the version with **Next release** or **Planned**, the title, **Set by hand** for a version set by hand, a progress bar with "\{done\}/\{total\}" over every issue in the release, and the worklanes that hold its issues, or **No issues yet**. The row opens the Timeline of the first of those worklanes, or of `main`, with the release in view. A repository set to not release shows **This repository does not release**.

Neither page plans, edits or moves releases: do that from a worklane's Timeline.

### The line under a worklane's name

Every worklane row, on Projects, an organisation's page, a project's repositories and Worklanes, shows one line under the worklane's name: the status and "\{ID\} \{title\}" of the issue it works on while Busy, "Next: \{ID\} \{title\}" while Free, or **Nothing queued** when no issue is left.

## Pin to the sidebar

A pinned project appears in your sidebar. Pinning is a personal preference and does not affect other members.

## Create, edit, and delete

Any workspace member can create and edit projects; only `owner` and `admin` can delete them.

<Callout type="warning">
Deleting a project does not delete its issues: they detach and stay in the workspace. The project's description is permanently deleted.
</Callout>
