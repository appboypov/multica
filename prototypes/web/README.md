# Steer all work: live prototype

Clickable MagicPath prototype of `designs/screens/steer-all-work.pen`: https://designs.magicpath.ai/v1/calm-water-3032

`src/` is the submitted MagicPath component source; the PNGs are screenshots of the hosted build at 1440 wide. The top-level PNGs are its screens: all projects grouped by organisation (`1-projects.png`), one project (`2-project.png`), a worklane's release timeline (`3-worklane-timeline.png`), the organisations (`4-organisations.png`), one organisation (`4b-organisation.png`), all worklanes (`4c-worklanes.png`), all releases (`4d-releases.png`) and New issue (`5-new-issue.png`).

An organisation groups the workspace's projects. The sidebar's Organisations item, in Work after Projects, opens the Organisations page: one row per organisation with its number of projects and repositories. A row opens that organisation's page, with its projects, repositories and worklanes as the same tree the Projects page shows. An organisation's group header on the Projects page opens its page too. Squads, Multica's groups of members and agents, are not part of this prototype: the sidebar's Squads item opens the same placeholder as the other items it leaves as Multica has them.

The sidebar's Worklanes and Releases items, in Work after Organisations, open pages that list all of them across the workspace, grouped by organisation, project and repository; each shows only the groups that hold worklanes or releases. The Worklanes page shows every worklane with the same columns as the Projects tree; a row opens that worklane's timeline. The Releases page shows every repository's release line in line order, one row per release, in the columns Name, Issues and Worklanes: its version chip in its state (shipped, next, planned) with its title, Set by hand as on the timeline and, for a shipped release, the day it shipped; its issue progress; and the worklanes that have issues in it. A row opens the timeline of the repository's first worklane that has issues in that release (else `main`) with that release in view; a repository that does not release keeps a row that says so. Planning, editing and moving a release stay on the worklane's timeline.

`created-issues/` shows an issue of every type made from its template on the hosted build: its page (`page-<type>.png`, `page-from-lane.png`), the worklane's Board view and the issue's preview there (`board.png`, `board-peek.png`, `peek-open-page.png`), and the worklane timeline with the issues in their release (`timeline.png`, `timeline-fresh.png`). The New issue dialog's "Fill example" fills a template with a worked example; it exists only in the prototype.

An issue's description is one Markdown field. The templates are the Markdown issue templates in `~/Work/the-archive` (`issue-management/templates/` for epic, story, bug, enhancement, refactor and chore; `linear/templates/` for spike and journey), without the sections that hold implementation details. The New issue fields only fill the chosen template's Markdown once; the issue keeps no separate fields. `markdown-description/` shows the dialog's Fields and Markdown tabs, the issue page's Preview and Markdown tabs, and an edit made in the Markdown.

Adding a repository, a worklane and a release follows `designs/creation-flows.md` and screens 6 to 8 of the `.pen` file. A repository is picked from what the GitHub App can see and checked out (or cloned) on a runtime; a worklane gets a folder that is unique in the project and a worktree that a runtime makes step by step; a release gets the repository's next version (Patch, Minor or Major, or Custom to set it by hand) and takes issues of the worklane that are in no release yet. `creation-flows/` shows these flows on the hosted build, from `1-add-repository.png` to `12-worklane-board.png`, where the planned issues are ready on the worklane's Board view. The runtime steps, the clone and the GitHub list are simulated in the prototype.

Editing and moving a release follows "Edit and move a release" in `designs/creation-flows.md` and screens 3b, 8b and 8c of the `.pen` file. `release-version/` shows on the hosted build a version set by hand that is too low and then accepted (`2-` to `4-`), an edit that renumbers later releases and one that clashes with a release set by hand (`5-`, `6-`), the line after moves (`7-`), a move refused with its reason (`8-`), and an issue that follows its release to the new number (`9-`).
